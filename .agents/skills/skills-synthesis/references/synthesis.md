# Selective synthesis

## What counts as a useful merge

The result must outperform the strongest suitable source on explicit criteria: fewer unsupported assumptions, clearer decisions, a missing functional capability within the same responsibility, safer execution, lower context cost, or better measured outcomes. More text is not a benefit. When the best single source already meets the goal, recommend that source or a narrow adaptation.

Classify all meaningful resources, not only instruction headings. A reference needs a named consumer; a script needs documented dependencies and a behavior test; an asset needs a use and redistribution rights. Discard unused boilerplate. Retain rich task-specific detail in focused references instead of flattening everything into the entrypoint.

## Resolving conflicts

Use this precedence for a synthesis decision: current user objective and authority, applicable target contracts, required safety/rights constraints, verified domain evidence, then source conventions. Do not let a source's aggressive activation or mandatory provider workflow override the target contract.

For each conflict, record both claims, supporting evidence, consequences, and the chosen rule. Resolve factual conflicts with current primary evidence or a safe reproduction. Escalate a material user preference or unresolved rights issue; do not invent certainty. Do not silently weaken a necessary guard merely because another source is shorter.

Examples:

- Two scripts implement the same transformation. Choose the one whose behavior and failure handling fit the task, or specify a tested original implementation. Do not keep both under ambiguous names.
- One source assumes a proprietary tool. Preserve the useful procedure with semantic capabilities and explicit fallback; exclude the adapter from the core.
- Two sources impose different approval rituals. Preserve actual user authorization and action boundaries, and remove redundant ceremony that changes neither.
- Sources target distinct outputs. Decompose them into separate skills instead of writing a mega-skill.

## Rights and provenance

Keep each source's immutable package identity and per-file hashes. The matrix links component → source → decision → target path → check. Copying requires compatible rights and retained notices. `pattern` reuse describes independently written logic, not copied material with its attribution removed.

## Acceptance cases for a merger

Exercise complementary skills, exact duplicates/mirrors, a strongest-source-only outcome, conflicting critical instructions, an unsafe script, missing license, and unrelated responsibilities. The resulting plan must explain every selection and rejection. Package creation and behavioral approval belong to later stages.
