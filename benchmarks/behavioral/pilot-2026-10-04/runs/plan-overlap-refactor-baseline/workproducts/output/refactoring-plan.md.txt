# Focused overlap refactoring plan

Status: proposal only. Implementation is not authorized. All supplied files remain in place; this execution creates planning documents under `output/` only.

## Evidence and recommendation

The inspected collection contains two packages and two catalog entries. Both entrypoints accept one supplied skill identity, a review request and evidence references, and produce one review-evidence note containing identity, review question, inspected artifacts, gaps and a reviewer handoff. Neither owns quality evaluation, execution of the reviewed skill, approval, installation or publication. The catalog descriptions and tags describe this same responsibility. The audit's overlap claim is supported by the actual entrypoints.

The useful differences are complementary resources: `skill-evidence-note/references/checklist.md` supplies ordinary assembly guidance; `skill-review-record/references/recovery.md` supplies missing-artifact recovery and protection against transferring evidence between same-named packages from different sources. They do not justify independent activation surfaces.

Recommend a final collection of **one canonical package, `skill-evidence-note`**, with one entrypoint and both reference resources. Consolidate the ordinary workflow into that entrypoint and retain recovery as an explicitly linked conditional resource. Do not introduce an orchestrator, a separate recovery skill, or a permanent compatibility package. Temporary compatibility during an authorized migration is distinct from the final collection.

### Naming decision

Both current names were reconsidered against the supplied collection. `skill-evidence-note` describes the artifact and evidence-organizing responsibility precisely. `skill-review-record` could imply a completed review or verdict even though its procedure explicitly produces an evidence note. A fresh name such as `skill-review-evidence-note` adds review context, but the canonical description already provides that context, and renaming both consumers offers no demonstrated benefit here. Retaining `skill-evidence-note` is therefore a semantic choice supported by the workflow and the smallest transition, rather than an assumption that existing names must survive.

No collision with this selected name exists among the two supplied catalog entries. Name availability in other collections is unknown and was not investigated. Source-qualified identity remains mandatory regardless of the selected package name.

Proposed final layout, not created in this execution:

```text
collections/review/
  skills-catalog.json                 # one canonical entry
  skills/
    skill-evidence-note/
      SKILL.md                       # sole workflow and activation surface
      references/
        checklist.md                 # ordinary evidence assembly
        recovery.md                  # missing artifacts and source collisions
      LICENSE                        # Apache-2.0
```

## Ordered handoffs and validation gates

These steps describe a later, separately authorized migration. This planning task stops before step 1 implementation work.

1. **Planner → future collection owner:** hand off this plan, resource mapping and preservation inventory. Owner must explicitly authorize implementation, assign package/catalog and consumer owners, confirm the transition window and decide the scope of unknown-consumer risk. **Gate: unresolved.** Neither the audit nor this proposal authorizes changes.
2. **Collection owner → migration maintainer:** capture a complete pre-change snapshot of both package trees and catalog in an authorized location outside skill discovery. Include baseline consumer references, inventory, hashes and a change manifest. Verify every snapshot file against the source and that a restore would return original paths and catalog together. Use a disposable staging location, never an installed collection. **Gate: snapshot integrity and restoration procedure demonstrated before edits.** No snapshots or restoration checks were performed here.
3. **Migration maintainer → content reviewer:** prepare the one-package candidate in authorized staging, preserving both references and license notices. Deliver a responsibility/resource crosswalk and proposed catalog change. **Gate: static review verifies no unique rule/example was dropped; all relative links resolve; frontmatter name, directory, catalog path, description and tags agree; catalog contains one final activation surface; no helper, provider or global lookup was introduced.** Keep baseline recoverable while review proceeds.
4. **Content reviewer → consumer owners:** assess candidate behavior with supplied, authorized examples. **Gate: ordinary note includes identity/question/inspection status/gaps/handoff without a verdict; unavailable `evidence/prior-output.md` preserves a gap and owner recovery request without invented success; two same-named packages retain separate sources and block ambiguous evidence use; an existing artifact does not imply a successful run; an unauthorized reference remains unopened and recorded as a limitation.** Confirm output stays in the chosen workspace. These are proposed scenario checks, not behavioral results from this exercise.
5. **Migration maintainer → workbook and runbook owners:** provide candidate paths and content plus the transition mapping. Runbook owner reviews its reference update and both retained recovery cases; workbook owner checks its stable entrypoint. **Gate: both acknowledgements are recorded and any actual reference edits have been reviewed; old recovery path remains usable for the whole agreed window.** Consumer files are absent here, so neither check is complete.
6. **Consumer owners → collection owner:** submit acceptance evidence and unresolved issues. Owner schedules a coordinated catalog/package/consumer cutover so no consumer points to a resource that is absent at that stage. Keep old paths through the window; narrow active discovery to the canonical package when owners confirm this is supported. **Gate: authorization, all prior gates, transition-window completion, rollback readiness, and explicit retirement decision.** Any unsupported catalog exclusion/alias behavior leaves retirement blocked until a concrete strategy is validated.
7. **Collection owner → post-migration reviewer:** after authorized cutover, verify the final package, single-entry catalog, resource links, licenses and the two consumer references together. Record actual checks and failures separately from this baseline audit. Preserve the migration snapshot for the owner-agreed retention period. Snapshot deletion, installation and publication require their own explicit authority and are not implied by the migration plan.

## Recovery and rollback

Use additive staging first: make canonical recovery guidance available and review it before changing the runbook reference or removing any old path. Do not overwrite or retire the only recoverable source during preparation. Track package, catalog and consumer edits as one migration manifest, including which consumers have switched; a package-only rollback can leave new recovery references dangling.

Rollback triggers include lost recovery guidance, unresolved relative links, ambiguous source identity, duplicate final activation, failed consumer acceptance or an unready transition window. Before cutover, stop and retain the baseline. After a partial cutover, restore from the verified snapshot and reverse affected consumer references and catalog changes together. Keep the new resource available until switched consumers have returned to working old references. Confirm original hashes, catalog resolution and both consumers' reference targets after restoration; preserve the failure evidence and report remaining gaps. Never fabricate validation success to unblock retirement.
